# BrowserPaw v4.1.2

- **Tag:** `v4.1.2`
- **Target:** `main`
- **Date:** 2026-11-02
- **Status:** Released

BrowserPaw 4.1.2 is a reliability release for the 4.1.1 interaction contract.
It aligns observation scope across execution paths, completes delayed page
ownership recovery, and makes expected page restrictions part of the normal
tool result path.

## Changes

### Interaction scope

- Standard DOM observation, fast snapshots, chained snapshots, locator checks
  and action preflight now share one interaction-scope calculation for active
  modal surfaces, Portals and scroll containers.
- Modal discovery follows native dialog/top-layer state, `aria-modal`,
  `aria-controls`, `aria-owns`, `popovertarget`, `commandfor`, composed Shadow
  DOM ancestry, and visible controls in the same overlay host. Framework class
  names remain discovery hints and do not grant interaction by themselves.
- Explicit background reads remain available, but modal and occlusion checks
  still block background actions.
- Scroll ownership is reported for the actual container instead of falling
  back to the background document when the target container is ambiguous.

### Fast observation

- Fast observation now honors `isolateModal:true` and `isolateModal:false` with
  the same active-modal reporting as standard observation.
- Options that fast observation cannot implement, currently `flattenCards` and
  `virtualizeViewport`, fail closed with `unsupported_fast_options` before the
  in-page observation. They no longer return a successful empty or degraded
  snapshot.

### Delayed page ownership

- A delayed page-creation identity can be recovered with
  `resume({adopt:true})` only after the same browser instance, agent ownership,
  tab and a concrete `documentId` are observed.
- A pending identity is never silently adopted. Known pending tabs and tab-less
  receipts can be explicitly retained with
  `finish({keepUnknownPages:true,confirm:true})`; neither path closes an
  unidentified page or claims cleanup.

### Expected page restrictions

- Chromium native error pages (`chrome-error://chromewebdata/`) are rejected
  before content-script injection. A tab that changes to an error page while an
  operation is in progress returns one actionable blocked result instead of the
  raw `Frame with ID 0 is showing error page` exception.
- Browser internal pages, extension pages, Web Store pages, error pages and
  cloud-metadata guards use one shared expected-page-restriction error type.
  Click, fill, keyboard, JavaScript, web-fetch, screenshot, upload, computer and
  the common tool dispatcher no longer write these expected results to
  `console.error`.
- Unexpected tool failures still retain their existing `console.error`
  diagnostics. This change suppresses noise; it does not hide unrelated faults.
- `read_dom` keeps its structured error-page degradation result, and
  `NetworkRequestTool` returns a structured error without attempting another
  content-script injection.
- Shared schema help, tool documentation and canonical skill mirrors describe
  the same fast-observation, pending-page and expected-page behavior.

## Compatibility

No public tool name changes. Scripts that depended on degraded fast snapshots
or silent pending-page adoption must migrate:

- unsupported fast options now return `blocked` before observation;
- delayed pending pages require explicit `resume({adopt:true})`;
- explicit finish retention requires `keepUnknownPages:true` and `confirm:true`.

Error text for browser internal, error and cloud-metadata pages is now explicit
and actionable:

- reload or navigate to a working page before retrying an error-page tab;
- obtain fresh refs after navigation;
- do not treat an expected page restriction as a bridge outage.

## Validation

- Complete `pnpm verify` (14/14) passed.
- Extension suite passed with 1775 tests.
- Native suite passed with 654 tests.
- `git -c core.whitespace=cr-at-eol diff --check` passed.
- The deployed extension artifact passed `verify:delivery`.
- The release commit and `v4.1.2` tag both passed GitHub Actions on Linux and
  Windows.
- A loaded runtime probe opened an isolated invalid host, attempted a network
  request from its Chromium error page, and received the friendly structured
  error. The owned probe page was then closed; existing user tabs were not
  modified.
- Release assets use the stable filenames `browserpaw-extension.zip` and
  `browserpaw-skill.zip`; the release tag carries the version identity.

## Boundaries

- The extension error-panel visual history is not cleared by reloading. New
  expected restrictions do not add entries through the fixed code paths, but
  clearing historical entries remains a user action.
- This patch does not restore the stopped M7 benchmark, change Jev mode
  authority, or alter successful browser actions.
- The published `v4.1.1` tag remains unchanged. The `v4.1.2` tag identifies
  this patch release and its Linux/Windows CI result and assets are recorded
  separately.
