# BrowserPaw v4.1.1

- **Tag:** `v4.1.1`
- **Target:** `main`
- **Date:** 2026-11-02
- **Status:** Released

BrowserPaw 4.1.1 converges the core browser path around one contract:

```text
observe current interaction scope
-> resolve one observed target
-> dispatch an explicit action
-> retain execution and verification facts
-> verify or hand back without replay
```

This is primarily a maturity and correctness release. It does not add a second
execution engine, restore the stopped M7 comparison, or claim universal site
reliability.

## Changes

- Standard DOM observations, fast snapshots, chained snapshots, locator checks
  and action preflight share modal, Portal and scroll-container scope results.
  Background text remains readable when explicitly requested; background
  actions remain blocked by an active modal or occlusion.
- Field commitment checks the field's value, selection, editability and native
  validation state. A nearby disabled control no longer turns a correct field
  write into a failed fill.
- `chrome_fill_index` and batch `fill` verify the field only. `pressEnter`
  records one explicit key dispatch. `submit:true` requires a caller-provided
  `submitTarget` and rejects the request before mutation when that target is
  absent. Combining Enter with an explicit submit click is rejected before
  mutation instead of dispatching two submission actions.
- `chrome_form_pipeline` fills the currently exposed form step without guessing
  a Next/Submit control or falling back to Enter. Use `chrome_batch_actions` for
  later explicit steps and assertions. Results distinguish
  `completionScope:"current_step_actions"` from `businessOutcome:"not_verified"`
  and retain fields proven complete before a later error.
- `chrome_batch_actions` validates every requested submit target and rejects
  conflicting follow-up actions before dispatching any step in the batch.
- Click, fill, interact, keyboard, batch and form results expose common
  `interaction.execution` and `interaction.verification` state. A dispatched or
  unknown action cannot be silently reclassified as a pre-dispatch failure.
- Actionability preflight rejects a target fully clipped by an ancestor scroll
  container; its geographic center is not treated as a valid hit point.
- Partial batch/form failures retain completed steps, stopping position and the
  original receipt. An `unknown` mutation stops the workflow with
  `retry:false`.
- Jev uses the same observed-target candidate set and execution result boundary.
  It may navigate, expand, toggle a local view, scroll and fill toward an
  explicit goal. Submit, send, publish and delete actions require caller-listed
  steps; model confidence is not authorization.
- Canonical skills and generated tool documentation use the same definitions as
  the runtime schema.

## Migration From 4.1.0

| 4.1.0 pattern                                                          | 4.1.1 behavior                                                                | Required migration                                                              |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `fill` with `pressEnter:true` described as a completed form submission | Enter is an explicit key dispatch; field verification remains field-only      | Add a separate result check or next action that proves the business outcome     |
| `submit:true` without a target                                         | Rejected as `blocked`, `requestDispatched:false` before field mutation        | Supply `submitTarget` using the existing strict locator fields                  |
| `pressEnter:true` together with `submit:true`                          | Rejected before mutation because both request a submission action             | Choose one explicitly authorized key or click step                              |
| `autoAdvance:true` on `chrome_form_pipeline`                           | Returns `migration_required` before changing a field                          | Use `chrome_batch_actions` with explicit fill, click/press_key and assert steps |
| Treating a nearby enabled button as proof of field commitment          | Field commitment is field-local; associated submit state is separate metadata | Inspect the desired business condition independently                            |
| Treating a last filled step as wizard completion                       | Form output distinguishes completed fields from later unexposed steps         | Continue with an explicit step or hand back the current state                   |
| Retrying after an unknown click/key result                             | Unknown means the action may have happened and remains `retry:false`          | Read fresh evidence before deciding whether a new action is safe                |

## Validation

The release requires:

- the complete `pnpm verify` suite and whitespace/diff checks;
- synchronized canonical/client skill trees and generated tool documentation;
- deterministic regression coverage for explicit submit boundaries, modal and
  Portal scope, scroll ownership, cancellation and unknown dispatch;
- eight real-browser flows covering a draft stopped before Send, document
  search, a controlled form, and a modal/Portal wizard;
- zero unauthorized submission, wrong-target dispatch or unknown-action replay;
- deployment hash verification and a loaded runtime identity matching the
  documented build.

Validation evidence belongs in the machine-local `.ego-research/` workspace and
must identify the actual build. It is not implied by source tests or a successful
upload.

## Boundaries

- Old scripts that relied on implicit form advancement are intentionally not
  source-compatible.
- Small real-browser acceptance samples do not prove reliability on every site.
- Hermes end-user acceptance remains with the user.
- Physical window resize/minimize tests remain waived and unverified.
- Native learned skills remain in `$BROWSERPAW_HOME/skills`; this release does
  not copy them into client plugin directories.
