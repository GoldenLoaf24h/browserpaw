# BrowserPaw v5.0.0

- **Tag:** v5.0.0
- **Target:** main
- **Date:** 2026-11-21

## Overview

> ⚠️⚠️⚠️ **IMPORTANT — Migration Required (For Users and AI Agents):** BrowserPaw v5.0.0 replaces the v4.x MCP server, persistent REPL, and client MCP wrappers with the `browserpaw` CLI and standard Agent Skill. Existing v4 MCP configurations (`127.0.0.1:12306/mcp`, stdio entries, and `chrome_*` tool bindings) will no longer work. Before using v5.0.0, read the [Migration Guide](../MIGRATION.md) ([Simplified Chinese](../MIGRATION.zh-CN.md)) to migrate your setup, or ask your AI Agent to read `docs/MIGRATION.md` (or `docs/MIGRATION.zh-CN.md`) and migrate your configuration automatically.

BrowserPaw v5.0.0 changes the product from an MCP server that exposes browser tools to Agent hosts into a CLI-first automation package. An Agent reads the installed BrowserPaw Skill, runs the `browserpaw` command, and uses the Chrome extension only as its connection to the user's browser. The library of operations now lives in one shared CLI command registry, while task IDs preserve ownership across separate CLI processes.

There is no `v4.2.1` release or tag. The `v4.2.0` work was an untagged local candidate and is incorporated into this release. Its browser-runtime fixes, DOM decomposition, historical regression migration and CLI/file-receipt groundwork remain part of v5.0.0; its temporary nine-tool MCP surface and persistent MCP-session CLI interface are not part of the final v5 command model because MCP and the REPL were retired. The comparison baseline remains the published `v4.1.2` tag.

## Changes

### CLI-first architecture and MCP retirement

- A shared command registry now defines browser commands, offline help, installed-version help and the generated command reference. Browser dispatch, argument parsing, task context and receipts use that registry instead of client-specific MCP schemas.
- The Native host now serves a versioned loopback protocol, and the Chrome MV3 extension performs browser work through Chrome Native Messaging. MCP HTTP, SSE, stdio, MCP SDK registration, dynamic tool discovery, the persistent REPL, Jev services, and legacy v4 MCP client wrappers are removed.
- The npm package provides `browserpaw` as its only public executable. It installs the CLI, Native host, Windows and POSIX host launchers, extension, recipes and Agent Skill. Quick Start recommends global Skill + npm (`npm install -g browserpaw@5.0.0 && browserpaw setup`) plus loading the unpacked Chrome extension; `npx browserpaw setup` uses the same command contract.
- Four unified v5 client plugins stay synchronized with `skills/browserpaw/` while leaving `~/.browserpaw` free for self-learned workflows: DeepSeek Harness (`plugins/browserpaw-dsh`, bundling the `browserpaw` npm package + read-only runtime skill + learned-index table), Hermes Agent (`plugins/browserpaw-hermes`, bundling the read-only `browserpaw:browserpaw` skill + single unified `browserpaw` CLI tool with gateway `MEDIA:` forwarding), Claude Code (`plugins/browserpaw-claude`, bundling the read-only skill + cross-platform `SessionStart` hook for CLI readiness and `~/.browserpaw` routing without top-level `bin/`), and ChatGPT/Codex (`plugins/browserpaw`, public-directory-eligible Portable Agent Plugins v1.0.0 base skill).
- Plugin-compliance hardening aligned all four client packages with their host specifications: Codex/ChatGPT ships `assets/icon.png`, `assets/logo.png`, `composerIcon`, `logo`, and `codex plugin add browserpaw@browserpaw` guidance; Claude Code keeps `.claude-plugin/` manifest-only (`assets/icon.png` moved out), adds a 10s `SessionStart` hook timeout, and documents Claude Code/Cowork/claude.ai data boundaries (passing `claude plugin validate --strict` and `--profile directory`); DeepSeek Harness prefers its bundled CLI over stale global `PATH`, renders the learned-workflow table after the skill body, and documents `dsh plugin --profile web exec browserpaw ...`; Hermes removes nonstandard `provides_middleware`, returns a JSON `media` array alongside `MEDIA:` lines with explicit model reply instructions, and documents the `--force --no-enable` v4 upgrade path (passing `hermes plugins validate --json` and `hermes plugins doctor --ci`).
- v5 uses the dedicated Native Messaging host name `com.browserpaw.nativehost` and default port `12307`. Setup installs the host outside the npm cache and registers it with Chrome; Chrome launches that host when the extension connects.
- The compact extension popup shows the live bridge connection and reads back the Agent Control, cursor and window settings from Chrome. Segmented controls and the switch keep their sliding animations, and the Agent Cursor and Window Mode rows keep their cursor icon and hint. The footer has a Star on GitHub link and marks the installed version with a red dot when a newer release is available. When no update exists, the version is inert with no tooltip or hover action. The bridge card and Jev settings are removed.
- The former default nine-tool MCP profile and exact per-tool activation are recorded as a v4.2.0 candidate stage and are superseded by the v5 CLI. The canonical browser behavior was retained without creating a second locator, task ledger, retry engine or browser execution service.

### Complete command surface and browser behavior

- The offline `browserpaw help` path lists the installed command surface, global targeting flags, exit codes and workflow. `browserpaw help COMMAND` returns command-specific usage and examples without opening Chrome; `tabs`, `open`, `nav`, `tab focus`, `tab close` and `status` cover page discovery and navigation.
- Observation and reading are available through `observe`, `text`, `find`, `wait`, `console` and scoped `network` commands. Screenshots can be saved to an explicit local file and return a capture ID for coordinate actions.
- Interaction commands cover physical click, hover, drag, keyboard input, scrolling, selection, multiline and rich-text fill, file upload, dialogs and explicit JavaScript, page-context fetch and supported CDP calls. Targets support observed refs, CSS, text, role and label locators, with strict frame and document identity checks.
- Durable `task start`, `open --task`, `batch`, `task status`, `task finish`, cancellation, borrowing and release retain task identity across CLI processes. Saved recipes and direct batches share the same step admission rules. The CLI stops at the first failed batch step and preserves prior step receipts and uncertain outcomes.
- `task resume --task ID --adopt` lets users and agents explicitly accept a recorded pending document after inspecting the page, including after same-URL form submissions. Recovery verifies browser, tab and document identity before further task actions or cleanup. It never repeats the action that caused the navigation.
- Dynamic pages retain the v4.2.0 fixes for transient DOM revision changes, main-frame observation when child frames fail, explicit incomplete frame coverage, stable tab affinity and fresh observations after navigation.
- Cross-frame work preserves iframe ownership, root-frame coordinate projection, encoded versus CSS screenshot dimensions and cached cursor state. Rich-text replacement uses trusted input without implicit submission, and dialogs and confirmation traps share bounded settle observation without uncontrolled retries.
- The DOM facade retains its public exports. Unused web fetcher, old click/fill injection helpers, the legacy computer executor, the detached API interceptor and the legacy undo executor with its action history are removed. Screenshot-coordinate and no-replay regressions exercise the active interaction path. The Native bridge uses fixed internal execution names.
- DOM sampling, frame result assembly and observed-ref state have separate modules behind the existing facade. The task manager keeps request sequencing while the ledger, page ownership and failed-creation compensation have separate implementations.
- DOM sampling and text extraction follow rendered Shadow DOM and slot assignments. Actionability checks use the exposed portion of partially covered controls and recheck clipping after scrolling. Text-based scrolling resolves the matching control or content element and reports measured movement, including the distance needed to bring an already rendered target into view.
- Internal action definitions carry execution and validation fields. The former MCP descriptions, unused form executor and Jev-only vision frame bookkeeping were removed. Active screenshot capture IDs still guard visual actions. CLI help and command search derive from the public command registry.
- Browser management has its own CLI commands. Use `history` to search visits and rank hosts (with past-relative `--since`/`--until` ranges such as `7d`), `bookmark` to organize, deduplicate or export folders, `downloads` to manage download records, `storage` to work with a selected origin, and `cookies` to inspect scoped cookie metadata or edit individual entries (with future-relative `--expires` offsets such as `7d`, ISO timestamps, or epoch milliseconds). Window and tab group commands work with explicit Chrome IDs.
- The `network` command family supports recording, filtering, inspecting individual requests, clearing entries and exporting textual bodies. `network show ID` uses the recorded ID from `network list`, which stays stable when the list is filtered. `console` supports level and text filtering. `perf`, `emulate` and `pdf` provide Chrome performance tracing, page emulation and local PDF files. The Chrome debugger is shared with the existing CDP execution path.
- The shared command registry groups offline help into page, reading, interaction, browser data, diagnostics, task and recipe topics. The base Skill links to short workflow references for data management and debugging. Internal execution names are independent of the upstream MCP list.
- `browserpaw search KEYWORD...` discovers commands offline from their names, descriptions, options and common English and Chinese keywords. It returns ranked usage and examples, with `--limit` and `--json` for Agent workflows.
- Help and search show `window list` for window IDs and `select TARGET` for available choices. The CLI accepts `tabs --windows` and `select TARGET --list` as compatibility spellings.
- Link extraction honors frame and target scope. A missing scoped target produces an explicit failure. Embedded page text stays literal even when it resembles JSON.
- Network recordings and retained results are scoped to the tab and task. Stopping a recording keeps its captured requests available for inspection and body export. Performance trace export supports captures that reached their configured duration before the stop command.
- Agent Control can pause browser operations while `status` and `doctor` continue reporting the running bridge and actual switch state.
- Successful commands return compact results or `--json` receipts. Failures carry status, dispatch information when known, and a no-retry receipt. Exit code `0` means success, `1` failure, `2` usage error, `3` disconnected and `4` outcome unknown. Observe again after an unknown result before deciding what to do next.

### Local files, downloads and runtime lifecycle

- Repository builds stay in the workspace. Extension deployment uses the explicit `pnpm build:deploy` command and `pnpm verify:delivery` checks the deployed files.
- Extension build IDs depend on extension and shared build inputs, manifest key and build mode. Editing release Markdown changes the verification fingerprint without requiring a reload. The artifact manifest still records file hashes for delivery verification.
- Screenshot, media and large-result delivery use local file references rather than placing image data in Agent context. The v4.2.0 CLI artifact groundwork is folded into the explicit CLI output and file paths used by the v5 browser handlers.
- Managed CLI receipts age out after seven days or when they exceed the 200 newest eligible receipts. The current request, concurrent recent outputs, active or paused task outputs and entries with unrecognized files are protected. Explicit `--out` paths belong to the caller.
- Page-triggered downloads require the observed browser download GUID and page provenance. Direct URL downloads verify the ID returned by Chrome before the CLI reports a local file path.
- Direct downloads accept both `--out DIR` and `--out=DIR`. Explicit tab or task selection takes precedence over the `BROWSERPAW_TASK` default.
- The CLI checks npm's stable release tag on a daily interval and reports each newer version once on stderr. Running `setup` with the new CLI refreshes the Native Host and the base Skills it manages in place, then restores their learned routing from user data. The Chrome extension is upgraded manually from the matching GitHub release ZIP.
- Task cleanup closes only verified owned pages, preserves borrowed pages and reports unknown pages or downloads. Cancellation stops later work without claiming that already dispatched browser effects were rolled back.
- Task cancellation can reach the host during an in-flight command. The ledger retains terminal tasks with unresolved page creation or owned-page recovery evidence.
- Task ledger hygiene and `task list` compaction: `BrowserTaskManager` retains all active tasks plus the 30 newest terminal tasks, persists the compacted `tasks.json` immediately on load when stale entries are pruned, and returns compact `task list` summaries (`id`, `name`, `goal`, `status`, `currentTabId`, timestamps, `pageCount`, `downloadCount`, optional `pendingCreationCount`) without page, download, or pending-creation URLs (full details remain in `task status ID`).
- Dedicated Window Mode (`agentWindowMode: "window"` / `newWindow: true`) in `chrome_navigate` now returns `created: true`, top-level `tabId`, and resolved `url` on newly created windows (matching tab-mode and fallback-window creation contracts), fixing `browserpaw open URL --task ID` and standalone `browserpaw open URL` when Window Mode is enabled.
- `browserpaw status` compares the loaded extension `buildId` against `BROWSERPAW_EXTENSION_SYNC_DIR` when `BROWSERPAW_HOME` is unset, preventing false `build_mismatch` errors on dev-synced unpacked extensions.
- The Native host and extension preserve bounded timeouts, connection-loss reporting and task ownership. The CLI does not take over another process's task, silently change sessions or retry a mutation whose dispatch state is unknown.

### Learned workflows and automatic Agent routing

- Verified site skills now live in `~/.browserpaw/skills`, saved CLI workflows live in `~/.browserpaw/recipes`, and both are indexed in `~/.browserpaw/learned-index.json`. This replaces versioned site-note state with one explicit learning root.
- `recipe list` and `recipe find` work offline and match active workflows by intent, bilingual aliases, keywords and URL domain. `recipe show` prioritizes the draft for inspection. `recipe run` uses the active revision when one exists.
- `recipe save` accepts reviewed JSON for a sequence of normal CLI argument arrays or proposes a verified read-only skill definition. Saved recipes begin as candidates in separate `.candidate.json` files, so an active workflow keeps running while a repair is pending. `recipe patch ID --step INDEX -- ARGS...` statically validates and replaces one candidate step. `recipe validate ID key=value` executes only read-only candidates before atomically promoting them; write-capable candidates stay manual. `recipe rm` removes a saved workflow or disables a learned skill. Credential-like values and transient tab, document, session and observed-reference identities are rejected.
- Failed recipe steps stop without replay and return the failed step index, command, unexpanded template, completed-step count, and bounded URL/title/control diagnostics from the existing task page. Candidate recipes stay out of `learned-index.json`, installed Skill routing and `matchedRecipes` until activation succeeds.
- `recipe run KEY=VALUE` resolves typed string, integer, number, boolean, object and array inputs from the workflow schema. URL placeholders are encoded while non-URL placeholders retain literal text. A standalone workflow that opens a page starts and cleans up a temporary task unless the caller supplies an existing `--task` or `--tab`; when `--tab ID` is supplied, `open` navigates the selected tab in place and subsequent steps remain bound to that tab without creating or leaving behind extra tabs.
- Saving, validating or removing a workflow refreshes the learned index and updates every recorded installed BrowserPaw `SKILL.md`. The generated routing section and frontmatter description contain IDs, sites and executable commands, so a future Agent can discover and call a learned site workflow without a user reminder.
- `open` and `nav` results include matching `matchedRecipes` hints for the target URL. Recipe matching is advisory; the Agent decides whether the inputs and current page state fit before executing the suggested command.
- `browserpaw setup` installs the baseline Agent Skill in the standard user scope at `~/.agents/skills/browserpaw` by default. `--skill-scope project` installs into the current project's `.agents/skills/browserpaw`, `--skill-dir DIR` selects a custom skills root and `--no-skill` skips installation. Later routing refreshes preserve these recorded scopes.

### Historical runtime reconciliation and cleanup

- The v4.2.0 candidate consolidated all tracked and untracked work after `v4.1.2`, including dynamic screenshots, frame observation, rich-text input, command receipts and the DOM module split.
- Four previously uncollected root test files were archived with their original bytes. Their useful behavior checks were migrated into collected extension and Native suites; duplicate or obsolete source-layout assertions were replaced by contracts for current behavior.
- The v4.2.0 release-governance work is retained: documentation ownership, release templates, release validation, raw verification evidence rules and archived historical records. Active setup and troubleshooting guidance now describe the CLI rather than the removed MCP configuration.
- Obsolete MCP examples, v4 MCP client wrappers, Jev benchmarks and adapters, REPL guidance, old tool matrices and skill scripts are removed from the active distribution. Learned user data under `~/.browserpaw` is not treated as disposable repository output.

### Packaging, generated documentation and quality

- Command documentation is generated from the shared registry, and all four client plugin Skill mirrors plus the packaged Native Skill remain synchronized from `skills/browserpaw/`. Multi-path installation choices and host plugin boundaries are documented in [INSTALL.md](../../INSTALL.md) and [PLUGIN_COMPATIBILITY.md](../development/PLUGIN_COMPATIBILITY.md). Help is installed with the CLI, so an Agent can discover the current syntax without a network request.
- The Hermes adapter only forwards image artifacts from a successful screenshot receipt in the request's managed output directory. Browser execution stays in the common CLI.
- Package smoke tests run `npm pack`, inspect the tarball contents, extract the real package into a clean temporary directory, and exercise the extracted CLI, setup, Skill/recipe loading, update notice and `LICENSE`. Production extension artifacts include build provenance for matching the loaded extension to the tested source.
- The CI matrix covers Linux, Windows and macOS. The Linux and Windows jobs run the loaded-extension fixture, which exercises the popup's Window Mode setting and compares actual Chrome window IDs and cleanup receipts.
- The v5 gate adds tests for command parsing, task continuity, CLI output, download provenance, self-learning storage, recipe matching and routing synchronization, while retaining the collected extension runtime regressions from the v4.2.0 reconciliation.

## Upgrade & Compatibility

- **Migration Guide (Users & Agents):** follow [docs/MIGRATION.md](../MIGRATION.md) ([Simplified Chinese](../MIGRATION.zh-CN.md)) for the complete v4-to-v5 checklist and command mapping table, or instruct your Agent to read the migration guide and execute the configuration cleanup and `browserpaw setup` workflow.
- **Breaking entrypoint change:** remove BrowserPaw HTTP and stdio MCP entries together with the old REPL and v4 MCP wrapper configs (`mcp_servers.browserpaw`, `mcp_allowlist`, and `@deepseek-ai/dsh-mcp-client` bridge setups). Complete or explicitly retain unfinished v4 tasks, install v5 via the recommended global Skill + npm Quick Start (`npm install -g browserpaw@5.0.0 && browserpaw setup`) or upgrade to the unified v5 client plugins (`plugins/browserpaw-dsh`, `plugins/browserpaw-hermes`, `plugins/browserpaw-claude`, `plugins/browserpaw`), and load the v5 extension path printed by setup.
- **Command migration:** use `tabs` and `observe` instead of separate window, tab and DOM tool calls; use `click`, `fill`, `select`, `press`, `scroll`, `drag` and `upload` for browser actions; use `task` for ownership and cleanup, `batch` for deterministic groups, `recipe` for learned workflows and `screenshot --out FILE` for image files. Run `browserpaw help` for the exact installed syntax.
- **Tool surface:** the v4.2.0 nine-tool MCP profile, `chrome_tool_docs`, temporary activation and Full MCP compatibility mode no longer exist in v5. The v4.2.0 persistent MCP-session CLI commands are also retired; v5 task IDs carry browser ownership across one-shot and batched CLI calls.
- **Skill installation:** the normal installation scope is `~/.agents/skills/browserpaw`. Project-local installation is available with `browserpaw setup --skill-scope project`; a custom target must use either `--skill-dir` or `--no-skill` rather than an ambiguous combination.
- **Learned state:** workflows are stored under `~/.browserpaw`. Existing verified skills should be placed in `~/.browserpaw/skills`, CLI workflows in `~/.browserpaw/recipes`, and the index is regenerated by save, validate, remove or setup operations. Recipes must not contain passwords, cookies, tokens, transient tab IDs or observed refs.
- **Runtime requirements:** Node.js 22.6 or later is required. BrowserPaw uses a dedicated Native Messaging identity and port `12307`; the extension must be loaded unpacked from the path printed by v5 setup. A v4 Native registration does not satisfy the v5 host protocol.
- **Later v5 upgrades:** follow the [installation guide](../../INSTALL.md#upgrade-an-existing-v5-installation). Preserve the existing CLI installation method, run setup with the new CLI, and load or reload the unpacked extension in `chrome://extensions`. Verify the loaded build with `status` or `doctor`.
- **Removed optional systems:** Jev, the persistent REPL, MCP HTTP/SSE/stdio servers, and v4 MCP-based Hermes/DSH wrappers are retired and are not compatibility targets for v5. Automation uses the `browserpaw` CLI, standard Agent Skill, learned workflows under `~/.browserpaw`, and the unified v5 CLI-backed client plugins.
